- `fn parent_crossover<U>(...)` inside which the `process_pair` closure currently calls `crossover::factory(parent_1, parent_2, configuration.crossover_configuration)?`
- The closure result is destructured via `child_2 = children.pop()`, `child_1 = children.pop()` (or similar — confirm exact lines during Read step)
- `process_pair` is invoked from either a `.par_iter()` (non-wasm) or `.iter()` (wasm) iterator behind cfg gates — the closure body itself is shared

Bound expansion required:
- `parent_crossover` already takes `U: LinearChromosome` (or whatever the current bound is post-Phase 47). Adding `+ RealValued` to that bound would break all non-real-valued chromosome users. Instead: the multi-parent branch must only call `factory_multi_parent` when the user has selected a multi-parent variant, and the call must compile for all `U: LinearChromosome`. SOLUTION: gate the call on a separate generic dispatcher that adds the `RealValued` bound — but Rust does not allow runtime addition of trait bounds.
- ACCEPTED APPROACH: expand the `parent_crossover` (or the relevant call-site function) bound from `U: LinearChromosome` to `U: LinearChromosome + RealValued`. This is consistent with the broader Phase 47 ChromosomeT split direction and acceptable because: (a) the standard `factory` accepts `U: LinearChromosome` and `LinearChromosome + RealValued` is a strict subset that still satisfies it; (b) all built-in real-valued chromosomes (`RangeChromosome`, `MultiRangeChromosome`) implement `RealValued`; (c) non-real-valued chromosomes (`BinaryChromosome`, `ListChromosome`) cannot use UNDX/SPX/PCX anyway and were the entire reason for the `RealValued` marker. **Confirm bound expansion is acceptable during the Read step by grepping for `parent_crossover` callers and ensuring all call sites use `RealValued`-implementing types.** If non-real-valued callers exist, instead split `parent_crossover` into two helpers and route by trait specialization — but the first-choice approach is bound expansion.

WASM safety:
- The `process_pair` closure body is reused across cfg-gated iterators per Pitfall 5. The new branch lives inside the closure, NOT around the iterator selection. No new `#[cfg(...)]` attributes required.

1-vs-2 offspring contract (Pitfall 1):
- Standard `factory` returns `Vec<U>` of length 2 (two children).
- `factory_multi_parent` returns `Vec<U>` of length 1.
- The pop order in the existing code is `child_2 = pop()`, then `child_1 = pop()`. With only 1 child, the multi-parent branch must invert: `child_1 = pop().unwrap()`, then `child_2 = parent_1.clone()` (or `parent_2.clone()`).
