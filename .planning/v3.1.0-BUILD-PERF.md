## Non-negotiable guarantees

Every action below MUST satisfy ALL of these before merge:

1. **Zero behavioural regression on default build** — `cargo run --example rastrigin` produces identical best-fitness (within 1e-12) for a fixed RNG seed before and after, captured in the regression harness described in §Cross-cutting work.
2. **Zero public-API regression on default features** — `cargo public-api` diff (or manual rustdoc diff for items annotated `pub`) is empty unless explicitly documented as a v3.x SemVer-additive change. Removals require `#[deprecated]` first for at least one minor release.
3. **All CI gates remain green** on every supported feature combination:
   - `default`
   - `serde`
   - `visualization`
   - `benchmarks`
   - `observer-tracing`
   - `observer-metrics`
   - All-features (`--all-features`)
   - WASM (`--target wasm32-unknown-unknown`, default features)
4. **Documentation surface stays accurate**:
   - `cargo doc --no-deps` zero warnings.
   - `README.md`, crate-level `src/lib.rs`, and the per-feature `docs/` guides reflect every flag change.
   - `CHANGELOG.md` records every change (Added / Changed / Removed) per Keep-a-Changelog.
   - `MIGRATION.md` records any behaviour change a v3.0 user could observe.
5. **Reversibility** — every action is committed atomically with a `Revert plan` line in the body so a future maintainer can undo it without archaeology.
6. **Measurement before and after** — every action emits a delta against the baseline (see §Baseline harness). A change that does not improve its declared metric is reverted, not "kept for hygiene reasons."

If any of these guarantees cannot be met for an action, the action does NOT ship; it is deferred or redesigned.

## Cross-cutting work (do FIRST, before any of the 10)

Three foundations must exist before action #1 starts. None of them ships value on its own; they exist to make the regression guarantee enforceable.

### CC-1. Baseline harness — `bench/build_perf.sh` + reference run

A scripted, reproducible measurement of:
- `cargo clean && cargo build --quiet --timings` (default features) → wall-clock and `target/cargo-timings/cargo-timing-*.html` archived
- `cargo clean && cargo check --target wasm32-unknown-unknown` → wall-clock
- `cargo clean && cargo test --quiet` → wall-clock
- `cargo bench --bench rastrigin -- --quick` → criterion baseline (or `divan` after #7)
- `cargo tree --prefix none | sort -u | wc -l` → dep count
- `cargo public-api` → API surface snapshot (saved in `tests/snapshots/public-api.txt`)
- `cargo run --example rastrigin --release -- --seed 42` → best-fitness golden file
- Same for `nsga2_zdt1`, `cma_es_rastrigin`, `pso_rastrigin` (one example per engine family)

Output is committed to `.planning/baselines/v3.0.0-baseline.json`. Each action's CI gate diffs against it.

**Deliverable**: PR opening v3.1.0 milestone with `bench/build_perf.sh`, `.planning/baselines/v3.0.0-baseline.json`, and a CI job that runs the harness and fails on regression > 2 %.

### CC-2. Feature-matrix CI

`.github/workflows/feature-matrix.yml` runs `cargo test` on every supported feature combination listed in §Non-negotiable #3 above. Currently the CI tests only `default` and `serde`. Without the full matrix, action #2 (gating `log`) and #3 (gating `rayon`) cannot be verified.

**Deliverable**: workflow file + green run on `main` before M2 starts.

### CC-3. Golden-output regression tests

`tests/golden/` containing deterministic seeded runs of the four reference examples with their expected best-fitness values to 12 decimals. Each refactor (#1, #3, #4) reruns these and panics on divergence.

**Deliverable**: test module + green run on `main` before M2 starts.

## Wave M1 — Config-only quick wins (zero behavioural change)

Each action below is a single PR. They can ship in any order and in parallel after CC-1 is in.

### Action #5 + #6 — Cargo profile tuning

**Files**: `Cargo.toml`

**Change**:
```toml
[profile.dev]
# debuginfo for line numbers in backtraces, no full DWARF.
debug = "line-tables-only"
# Default split-debuginfo on macOS is slow; line tables alone shave seconds.
split-debuginfo = "unpacked"

[profile.dev.package."*"]
# Optimise dependencies once; speeds up runtime tests on rand/rayon/log
# at the cost of ~5–10 s on first build (one-time, then cached).
opt-level = 1
debug = false

[profile.test]
# Tests run a lot of GA generations; -O1 cuts runtime ~50 % at no rustc cost.
opt-level = 1
```

**Why no regression**: profiles affect codegen, not API or behaviour. Numerical results of the GA are byte-identical (we run in fp64, not in fp-fast-math).

**Verification**: CC-3 golden tests + CC-1 baseline diff. Expect baseline build wall-clock to improve immediately on second build.

**Docs**:
- `CHANGELOG.md` → "Changed: optimised default dev profile for faster local builds; no API change."
- `docs/DEVELOPMENT.md` → "Cargo profiles" section explaining the choice.
- `.planning/intel/build-profile.md` → AI-readable note on why these specific knobs.

**Revert plan**: delete the four profile blocks.

### Action #9 — Explicit linker config (mold on Linux, lld on Windows/macOS)

**Files**: `.cargo/config.toml`

**Change**:
```toml
[target.x86_64-unknown-linux-gnu]
linker = "clang"
rustflags = ["-C", "link-arg=-fuse-ld=mold"]

[target.x86_64-apple-darwin]
# macOS 15+ ships a fast default linker; only override if asked.

[target.aarch64-apple-darwin]
# Same: rely on the platform linker.
```

Document the optional path:
```toml
# Uncomment for ~5 % faster macOS builds (requires `brew install llvm`):
# [target.aarch64-apple-darwin]
# rustflags = ["-C", "link-arg=-fuse-ld=lld"]
```

**Why no regression**: linker choice affects output binary layout, not ABI or behaviour. Tests verify.

**Verification**: CI runs on Linux + macOS + WASM and golden tests pass.

**Docs**:
- `docs/DEVELOPMENT.md` → "Linker recommendations" section.
- `CHANGELOG.md` → "Changed (CI): Linux CI uses mold linker; opt-in for local dev."

**Revert plan**: delete the `[target.*]` blocks.

## Wave M2 — Dependency hygiene (smallest user-visible surface)

These two actions touch the published crate. They require a minor SemVer bump (v3.1.0).

### Action #1 — Remove `env_logger` auto-install; move dependency to dev-deps

**Files**: `Cargo.toml`, `src/engines/ga.rs`, `examples/*.rs`, `CHANGELOG.md`, `MIGRATION.md`, `docs/getting-started.md`

**Diagnosis**: `src/engines/ga.rs:1588` calls:
```rust
let _ = env_logger::Builder::from_default_env()
    .filter_level(log_level)
    .try_init();
```
This is an anti-pattern. Libraries should never install loggers; the application chooses (env_logger, fmt-subscriber, slog, journald, …). Today `env_logger` is in `[dependencies]` purely to power this auto-init. That pulls in `regex`, `aho-corasick`, `memchr`, `regex-automata`, `regex-syntax`, `anstream`, `anstyle`, `anstyle-parse`, `anstyle-query`, `colorchoice`, `is_terminal_polyfill`, `humantime`, `env_filter` — **~12 crates of build cost** per user.

**Change**:
1. Delete the `env_logger::Builder::...` block in `ga.rs`. The GA continues to emit `log!()` events as today; users install whichever subscriber they want.
2. Move `env_logger` from `[dependencies]` to `[dev-dependencies]` so examples can keep using it.
3. Update every example that relied on the auto-installed logger to do `env_logger::init()` in `main()` explicitly.
4. Drop `LogLevel` plumbing if it ONLY existed to feed the auto-init (verify first; it may still feed `log_level!` filters that users observe through their own subscriber).

**Why almost no regression**: end users who *never observed log output* see no difference. End users who **did** observe log output without ever calling `env_logger::init()` themselves will stop seeing logs until they add `env_logger::init()` (one line, documented in MIGRATION.md). This is a behavioural change, hence the M2 minor bump.

**Verification**:
- CC-3 golden tests (numerical output unchanged).
- New test `tests/test_no_logger_installed.rs` asserts the GA does not install a logger when none is configured.
- Manual: run every example with and without `RUST_LOG=info` and document expected output.

**Docs**:
- `CHANGELOG.md` v3.1.0 → "Changed (mildly breaking): the GA no longer auto-installs `env_logger`. Users wanting log output must call `env_logger::init()` (or use any other `log` subscriber). Motivation: removes 12 transitive deps and ~25 % build time."
- `MIGRATION.md` → new section "Upgrading from v3.0 to v3.1: logger setup".
- `docs/getting-started.md` → updated "Quick Start" snippet adds `env_logger::init()`.
- `README.md` → "Logging" subsection updated.
- `.planning/intel/logger-history.md` → record the rationale + the date so future maintainers don't reintroduce the anti-pattern.

**Revert plan**: re-add `env_logger` to `[dependencies]` and restore the four-line `try_init()` block. Documented in the commit body.

### Action #2 — `log` behind a `logging` feature (default-on)

**Files**: `Cargo.toml`, `src/**` (every `use log::*` site), feature-matrix CI

**Change**:
```toml
[features]
default = ["logging"]
logging = ["dep:log"]
```

Every `log::info!`, `log::trace!`, … call site is wrapped:
```rust
#[cfg(feature = "logging")]
log::info!(target = "ga_events", "…");
```
Or, preferred, hidden behind a tiny internal macro `crate::log_info!()` that expands to a no-op when `logging` is off.

**Why no regression on default**: feature is default-on. Users who don't override defaults get the exact behaviour they have today.

**Why this helps**: power users who want minimal binary size and minimal build time (embedded, wasm) get `default-features = false` and shed the `log` crate.

**Verification**: feature-matrix CI gate (CC-2) compiles with and without `logging` enabled.

**Docs**:
- `CHANGELOG.md` → "Added: `logging` feature (default-on); disable with `default-features = false` for ultra-lean builds."
- `README.md` Features table → row added.
- `src/lib.rs` Feature Flags table → row added.
- `MIGRATION.md` → not needed (default behaviour unchanged).
- `.planning/intel/feature-flags.md` → AI-readable note on the feature-flag philosophy.

**Revert plan**: drop the feature, remove the gates.

## Wave M3 — Major refactors (highest risk, biggest payoff)

These are NOT bundled into v3.1.0. They each become their own phase in v3.2.0 (or later) once M1 + M2 ship and the baseline is established.

### Action #7 — `criterion` → `divan`

**Files**: every `benches/*.rs`, `Cargo.toml`, CI bench workflow

**Diagnosis**: `criterion` is a dev-only dep but adds ~25 transitive crates to `cargo bench` builds. `divan` (cargo-divan) is a modern replacement with similar UX and a fraction of the dep weight.

**Change**: port each bench file one at a time. Keep both runners side-by-side for one release cycle; remove criterion at the start of v3.3.0.

**Why no regression on builds without bench**: `[dev-dependencies]` only affects `cargo test`/`cargo bench`. Default user builds unchanged.

**Why care if it's dev-only**: developer iteration time + CI bench job wall-clock. Criterion compiles slowly the first time.

**Verification**: each bench file's median value pre- vs post-port within ±3 % on the same machine (intra-machine noise dominates).

**Docs**:
- `CHANGELOG.md` v3.2.0 → "Changed: bench harness migrated from criterion to divan."
- `docs/benchmarks.md` → updated invocation snippets.
- `.planning/intel/bench-harness.md` → AI-readable rationale.

**Revert plan**: each bench file's port is atomic; revert individually if needed.

### Action #3 — `rayon` behind a `parallel` feature (default-on)

**Files**: every `par_iter()`, `par_iter_mut()`, `par_chunks*()`, `into_par_iter()` site (~60 across the crate), `Cargo.toml`

**Diagnosis**: today `rayon` is unconditional. Users on wasm32 (no threads) already get sequential fallback at every site (CLAUDE.md mandates the pattern). Power users on tiny single-thread environments could shed `rayon` + `crossbeam-deque` + `crossbeam-epoch` + `crossbeam-utils` (4 crates) plus the runtime cost of spawning a thread pool.

**Change**:
```toml
[features]
default = ["parallel", "logging"]
parallel = ["dep:rayon"]
```
Every parallel site already has a `#[cfg(target_arch = "wasm32")]` sibling that uses `.iter()`. Replace the gate with `#[cfg(any(target_arch = "wasm32", not(feature = "parallel")))]`. The serial side becomes the canonical fallback; the parallel side becomes the opt-in.

**Why no regression on default**: feature default-on means every existing user gets the same parallelism.

**Why this is risky**: ~60 sites. Easy to miss one. Mitigation: a `clippy::custom_lint` rule (or a regex CI check) that forbids unconditional `rayon::` references in `src/` would have caught this for v3.0; introducing it here documents the invariant.

**Verification**:
- Feature-matrix CI (CC-2) compiles with `--no-default-features --features logging,parallel,…` combinations.
- CC-3 golden tests for `parallel=on` AND `parallel=off`. Identical numerical output proves the parallel-vs-serial divergence is purely scheduling.
- WASM check unchanged (the wasm gate already routes through the serial path).

**Docs**:
- `CHANGELOG.md` v3.2.0 → "Added: `parallel` feature (default-on). Disable to shed rayon + crossbeam (~4 transitive deps) for embedded / wasm-only builds."
- `README.md` Features table → row added.
- `src/lib.rs` Feature Flags table → row added.
- `MIGRATION.md` → not needed (default behaviour unchanged).
- `CLAUDE.md` "WASM Compatibility" rule updated: gate is now `#[cfg(any(target_arch = "wasm32", not(feature = "parallel")))]`.
- `.planning/intel/parallel-feature.md` → AI-readable rationale + the canonical gate pattern.

**Revert plan**: drop the feature, ungate every site. Atomic.

### Action #4 — Refactor `engines/ga.rs` (139 KB → cohesive submodules)

**Files**: `src/engines/ga.rs` (current 3700+ lines) → `src/engines/ga/mod.rs` + submodules

**Diagnosis**: one file = one rustc compilation unit for the front-end; codegen-units cannot help. Splitting enables rustc to parallelise.

**Proposed split** (one submodule per cohesive concern):
- `ga/mod.rs` — `Ga<U>` struct, `with_*` builders, `build()`, `run()` orchestrator
- `ga/lifecycle.rs` — `init_population`, `evaluate_initial_fitness`, `finalise_run`
- `ga/generation.rs` — the per-generation loop (selection → crossover → mutation → survivor)
- `ga/adaptive.rs` — adaptive crossover/mutation probability recomputation
- `ga/aos.rs` — Adaptive Operator Selection integration in the loop
- `ga/extension.rs` — extension trigger + diversity check
- `ga/cache.rs` — fitness cache lookup / insertion
- `ga/batch.rs` — `batch_evaluate_pop` helper
- `ga/stats.rs` — `GenerationStats` collection
- `ga/observer.rs` — observer hook dispatch
- `ga/stopping.rs` — stopping-criteria check

**Why no regression**: pure code movement. No semantics change.

**Mitigation against silent regression**:
- Pre-split: capture the file's symbol table (`cargo expand`) and diff against post-split.
- CC-3 golden tests on all four reference examples.
- Full feature-matrix CI.

**Docs**:
- `CHANGELOG.md` v3.3.0 → "Changed (internal): `engines/ga.rs` split into submodules; no API change."
- `docs/ARCHITECTURE.md` → updated module map.
- `.planning/intel/ga-internals.md` → AI-readable submodule responsibilities (so future code-edits land in the right file).

**Revert plan**: `git revert <commit-sha>` of the refactor. Atomic.

## Acceptance gate per action

A PR that implements one of the 10 actions is mergeable iff:

1. The CC-1 build_perf script run on the PR branch shows ≥ the declared Δ on at least one of {dev build, CI build, dep count}, within noise tolerance.
2. The CC-3 golden tests pass byte-identically.
3. The CC-2 feature-matrix CI is green on every supported feature combination.
4. WASM check passes (or is unaffected for CI-only actions).
5. `cargo public-api` shows zero unintended changes.
6. `cargo doc --no-deps` zero warnings.
7. The documentation index above is updated for every audience the change touches.
8. The commit body contains a `Revert plan: <verb> <object>` line.
9. The PR description links the baseline diff and the post-change measurement.

A PR that fails ANY of the 9 gates is not merged; it is sent back for redesign.

## Open questions / decisions to confirm before kickoff

1. **SemVer policy on default features**: making `log`, `rayon` default-on means downstream `default-features = false` users today already opted out — but they got the env_logger anyway. We should confirm whether v3.x will treat dependency removal as patch / minor / major. **Recommendation**: minor (v3.1, v3.2) is industry-standard.
2. **Which Linux runner has mold installed by default**: `ubuntu-22.04` does NOT; we install via `apt-get install -y mold`. Adds ~5 s to CI cold start; net win still positive.
3. **`logging` feature naming**: `log` collides with the `log` crate name in some toolchains. Use `logging` (not `log`).
4. **`parallel` vs `rayon` feature name**: prefer `parallel` (semantic) over `rayon` (implementation detail). Lets us swap implementation later without another breaking flag change.

Decisions are captured in the corresponding `.planning/intel/*.md` once approved.
